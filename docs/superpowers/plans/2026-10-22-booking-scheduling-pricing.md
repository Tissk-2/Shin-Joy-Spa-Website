# Booking Scheduling and Pricing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a shared room schedule and correctly priced, staff-approved pay-at-spa bookings, with the lifecycle hooks needed by online payments.

**Architecture:** Keep existing Laravel actions, presenters, and Inertia pages. Add a short database-serialized allocation boundary shared by every schedule writer, explicit authorized booking actions, and immutable quote/occupancy snapshots. Use the baseline transactional outbox for consequences of committed changes.

**Tech Stack:** PHP ^8.3, Laravel ^13.0, PHPUnit ^11.5.3, Vue 3, TypeScript, Vitest, Playwright; production database engine must be verified before concurrency acceptance.

**Spec:** [Approved design](../specs/2026-10-22-booking-availability-payments-design.md), especially sections 2–6, 10, 12–16. Read the [master plan](2026-10-22-booking-implementation.md) and [baseline prerequisite](2026-10-22-booking-baseline.md).

## Global Constraints

- Full online payment after staff approval, or payment at the spa.
- Pending requests do not reserve rooms.
- Keep the entire group in one suitable room. No automatic split across rooms.
- 60 minutes after approval, capped at appointment start. Display the exact deadline.
- No automatic conversion to pay-at-spa. The customer can submit a new request.
- This release has no rescheduling and no cancellation cutoff for refund eligibility.
- Asia/Jakarta for input/display; UTC instants and integer IDR internally; existing quotes remain unchanged.
- `OutboxWriter::record(string $type, string $deduplicationKey, array $payload): OutboxMessage` runs within the business transaction; no network calls under allocation locks.
- Product implementation must preserve unrelated working-tree changes. New behavior remains disabled until its required settings and migration checks pass.

## Review Focus

1. A legacy database has enum/check constraints and existing rows: expanded statuses/roles must work after upgrade, not just fresh migration — B1/B4 `test_upgrade_preserves_legacy_rows_and_accepts_new_values`.
2. A therapist-dependent group fits a room but cannot be served: the approval action records staff suitability attestation; public availability does not promise therapists — B4 `test_approval_records_operational_attestation`.
3. A delayed availability response belongs to an old treatment selection: ignore it rather than replacing current slots — B5 `ignores_stale_availability_response`.
4. Two different accounts approve overlapping requests concurrently: at most one can occupy the last suitable room — B6 `test_separate_process_approvals_cannot_overlap`.
5. An accountless walk-in is submitted twice: one booking, the actual contact snapshot, and no accidental attachment to staff or a matching email account — B5 `test_manual_submission_replay_keeps_customer_identity`.

## File and interface map

New files are assigned in the tasks below; additions are proposals unless marked complete, existing files are verified paths. Migration timestamps `2026_10_22_010000` through `010006` are reserved for this plan; `010005` is the B3b guard and room-type migration, and `010006` adds B3c operational attestation to status history. B3g adds `2026_10_25_010007_add_room_block_terminations.php`; B3h adds `2026_10_26_010008_create_booking_settings.php`. Baseline migrations use an earlier range; Telegram/payments use later ranges.

Shared contracts produced here:

- `App\Support\ActionContext`: readonly constructor `(string $channel, ?string $ipAddress = null, ?string $userAgent = null, ?string $externalActorId = null)`. Closed channels: `dashboard`, `telegram`, `system`, `cli`. Never put provider/Telegram IP into a human actor field.
- `App\Support\Scheduling\ScheduleLock::run(Closure $operation): mixed`: transaction plus a real update of singleton guard row before conflict reads. Nested calls use the existing guard/transaction; retry the whole outer transaction at most three times for recognized transient conflicts.
- `App\Support\Bookings\BookingMutation::run(int $bookingId, Closure $operation): mixed`: schedule guard, locked booking reload, then `$operation(Booking $locked)`. Authorizes nothing by itself.
- `App\Support\Bookings\BookingStateWriter::transitionLocked(Booking $booking, BookingStatus $next, string $reason, ?User $actor, ActionContext $context): Booking`: internal state/audit/version/outbox writer; requires the mutation transaction and legal transition. Staff entry points establish current authorization; trusted workers pass a null actor with system context.
- `App\Support\Scheduling\RoomAllocator::allocateLocked(Booking $booking): RoomReservation` and `releaseLocked(Booking $booking, string $reason, CarbonImmutable $releasedAt): void`: require the same guarded transaction. Release does not decide financial or physical eligibility.
- `App\Actions\ApproveBooking::__invoke(User $actor, int $bookingId, BookingStatus $expected, ActionContext $context): Booking`.
- `App\Actions\CancelBooking::__invoke(User $actor, int $bookingId, BookingStatus $expected, string $reason, ActionContext $context): Booking`.
- `App\Actions\CompleteBooking::__invoke(User $actor, int $bookingId, BookingStatus $expected, ActionContext $context): Booking` and `RecordNoShow` with the same signature.

Every named event carries `booking_id:int` and `booking_version:int`. Creation uses version 1. Pending→confirmed/awaiting_payment emits `booking.approved`; awaiting_payment→confirmed emits `booking.confirmed`; terminal transitions emit `booking.cancelled`, `booking.completed`, or `booking.no_show`. An online approval additionally records `payment.session.requested`. Event dedupe uses type plus booking/version. `reason` and refund eligibility are persisted, not inferred from notification text.

Human mutations acquire `StaffAccessLock` before `ScheduleLock`/`BookingMutation` and recheck the actor under that guard. System jobs start with the schedule guard and never acquire the staff guard afterward. This includes manual booking creation, inventory edits, approvals, cancellations, and later payment/refund recording; follow the master-plan global lock order.
